# レート予測(レートエスティメーター)

個人ページの「レート予測」とクラブ内ランキングの「○○まで パフォ」は、
次のコンテストのパフォーマンスでレートがどう動くかを、AtCoder 公式の計算式で求めている。
計算は `src/lib/ratingEstimate.ts`、表示は `src/components/RatingEstimator.tsx` と `src/pages/ClubPage.tsx`。

## 式(アルゴリズム部門)

レート対象(Rated)の回のパフォを P_1, P_2, …, P_n とする(P_1 が最新)。

```
R = 800 · log2( Σ 2^(P_i / 800) · 0.9^i  /  Σ 0.9^i ) − f(n)
f(n) = ( √(1 − 0.81^n) / (1 − 0.9^n) − 1 ) / (√19 − 1) × 1200
R ≤ 400 なら R = 400 / exp((400 − R) / 400)
```

最後に四捨五入した値が表示されるレートになる。f(1) = 1200 なので、初回はパフォから 1200 引いた値(400 以下はさらに写す)になる。

## 実データでの照合(2026-11-09)

`users/<id>/history/json` の `Performance` を古い順に入れると、各回の `NewRating` と次のとおり一致した。

| ユーザー | Rated の回数 | 一致 |
| --- | --- | --- |
| mocaluna | 49 | 49 |
| n_ha_1050 | 199 | 199 |
| iroha_afternoon | 37 | 37 |
| tourist | 72 | 72 |

- `InnerPerformance`(上限で頭打ちにする前の値)を使うと、tourist の 72 回のうち一致は 27 回だけだった。
  上限に当たった回からずれるので、`Performance` を使う。
- mocaluna の 49 回はテスト(`tests/ratingEstimate.test.ts`)に入れてある。
- 四捨五入は `Math.round` にしている。ちょうど .5 になる回は無かったので、丸め方の違い(偶数への丸めなど)は確かめられていない。

## データ

- スナップショット(`scripts/build-snapshot.mjs`)は部員全員の参加履歴をもともと取っている。
  `rating-history.json` の各点に、その回のパフォ `p` を足した(追加のリクエストは無い)。
- 取得に失敗して前回分を使った部員の点には `p` が無いことがある。その人の個人ページには「データ更新待ち」と出し、ランキングには出さない。
- atcoder.jp は CORS を返さないので、本番で予測できるのは部員だけ。

## 「何パフォ以上なら」の求め方

新しいレートはパフォについて単調に増えるので、整数のパフォを [−4000, 6000] で二分探索する。
大きな ABC の最下位は −600〜−900 になることがあるので、下は広く取っている。

| 表示 | 求め方 |
| --- | --- |
| 次の色に上がる | 表示レートが次の色の境目以上になる最小のパフォ |
| レートが上がる | 表示レートが今より大きくなる最小のパフォ |
| 今の色から下がる | 表示レートが今の色の境目未満になる最大のパフォ。−4000 でも下がらなければ「次の1回では下がりません」 |
| 目標のレート(1〜3回続けて) | 同じパフォを k 回続けて目標以上になる最小のパフォ |
| 何回で次の色 | 同じパフォを続けて、境目に届く回数(30 回まで) |

レートが色の境目より十分上にあると、どんなに低いパフォでも1回では下がらない。
例: レート 568 の人は、パフォ −4000 でも 522 までしか下がらない(重みが 0.9 倍ずつで、低いパフォの 2^(P/800) はほぼ 0 になるため)。

## パフォの目安(どのくらいの問題に当たるか)

「パフォ 800」のような数字だけでは分かりにくいので、そのパフォくらいの実力で ABC の問題をどのくらい解けるかを、
「ほぼ毎回解ける A・B・C / 2回に1回くらい D / たまに解ける E」のように分けて出す(`src/lib/perfGuide.ts`)。

- AtCoder Problems の難易度(`problem-models.json` の `difficulty` と `discrimination`)は、
  「そのくらいの実力の人がコンテスト中に解ける確率」の 2PL ロジスティックモデル(`irt.ts` の `solveProbability` と同じ)。
- パフォを実力とみなし、最近の ABC 20 回(7問そろっていて、難易度が仮でない回)の A〜G ごとに、解ける確率を平均する。
- 区分は、解ける確率で分ける。10% 未満の問題は出さない。
  - 80% 以上: ほぼ毎回解ける
  - 35〜80%: 2回に1回くらい
  - 10〜35%: たまに解ける
- はじめは「C までほぼ解けて、D が半々くらい」という一文にしていたが、分かりにくいという声があり、区分に分ける形にした(2026-11-09)。
- 2026-11-09 時点(ABC464〜483)の値。

| パフォ | A | B | C | D | E | F | G |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 400 | 99% | 96% | 50% | 20% | 3% | 0% | 0% |
| 800 | 100% | 99% | 81% | 55% | 15% | 2% | 0% |
| 1200 | 100% | 100% | 95% | 86% | 43% | 9% | 1% |
| 1600 | 100% | 100% | 99% | 97% | 74% | 32% | 5% |

実際のパフォは、解いた問題の数に加えて、早さやペナルティでも変わる。そのため、これは「そのくらいの実力の人が解ける確率」の目安。

## 限界

- ABC のパフォの上限は 2400 として注記している(パフォの上限は Rated 対象の上限 + 400、ABC は 1999 まで、という AtCoder のルールから)。
  - 手元の履歴には、ABC で上限に当たった回が無かった(頭打ちは 2016 年の ARC の 3200 だけ)。
  - ARC・AGC の上限は区分ごとに違うので、注記には出していない。
- Unrated の回は計算に入れない(AtCoder と同じ)。
- 新しいコンテストは、レートの更新のあとのデータ更新(6時間ごと、土日の夜は 22:45〜0:00 にも)で反映される。
